# ADR-0012: Evaluation methodology for the agent

- Status: accepted
- Date: 2026-10-08

## Context

The agent has to be measured, not demonstrated. The measurement must be reproducible on
an 8 GB laptop without a cluster, honest about uncertainty with only 30 scenarios, safe
(no evaluation may change anything without the same approval path a person would use),
and resistant to the agent being tuned towards the answers. A full matrix of five
retrieval configurations on every case would take about four hours of local model time.

## Decision

- **Ground truth from injected faults** (ADR-0003): 30 scenarios, two per category, each
  with a verified symptom, an alert written at the symptom level, and ground truth
  (category, component, expected runbooks, acceptable fixes).
- **Record once, replay many times** (ADR-0008): every scenario and a healthy baseline are
  recorded through the production read tools; CI fails if a scenario file changes after
  its recording.
- **Dev/test split** (10/20) fixed in `evals/agent/splits.yaml`. Changes are made from dev
  failures; any change made because of a test result is disclosed in the report and every
  config is rerun.
- **Simulated approval in replay.** The harness approves the proposal so the run reaches
  its report; replay mode cannot execute anything, and the proposal is scored as
  proposed. The live subset uses the real approval path with approver `eval-harness`,
  approving only an acceptable fix for the true component.
- **Metrics with Wilson 95% intervals**, defined as `None` where they do not apply, and two
  safety metrics that must be zero: injected instructions followed, actions without an
  approval decision.
- **Reduced matrix** (agreed before running): C3 on all 30 cases and the control; C0 (no
  RAG) and C2 (no rerank) on the 20 test cases; five live cases. C1 and C4 only swap the
  vector store, which the Day 2 retrieval evaluation already compares; they stay
  implemented and can be run with `--configs C1,C4`.
- **The agent reranks by default (C3).** ADR-0004 left reranking off for interactive
  search because it costs about one second per query; inside an agent run that takes two
  minutes, that second is noise, so the agent's own retrieval step reranks.
- **Caching by content**: a run's outcome is keyed by case, config, prompt versions, a
  hash of the agent code and prompts, the fixture and the model, so interrupted runs
  resume and any code change reruns everything affected.
- **A leakage test** fails if a scenario id or any distinctive injected value appears in
  the agent's code or prompts.

## Alternatives considered

- **LLM-as-judge scoring.** Useful for free-text quality, but the questions here
  (category, component, cited runbook, action type) have exact answers, and a judge model
  on this laptop would double the runtime and add its own errors.
- **Live runs for every case.** The most realistic, but slow (inject, settle, reset), not
  reproducible, and it would need the cluster and the model in RAM together for hours.
- **The full five-config matrix.** About four hours; the store-only configs answer a
  question the retrieval evaluation already answered.
- **Bootstrap intervals.** Equivalent in spirit; Wilson intervals are closed-form, exact
  enough for proportions and behave at 0% or 100%.

## Consequences

- Every number in `evals/REPORT.md` is regenerated by `opspilot eval report` from
  committed result files; the README quotes the headline block, and a unit test fails if
  the two differ.
- With n=20 the intervals are wide (about ±20 points); the report treats differences
  inside them as inconclusive.
- Replay cannot show how a fault evolves or how the cluster reacts to a fix; the live
  subset covers that for five cases only.
